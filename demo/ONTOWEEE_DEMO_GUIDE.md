## 1. What is OntoWEEE?

OntoWEEE builds a knowledge graph about waste electrical and electronic equipment, usually abbreviated as **WEEE** or called **e-waste**. It uses language-model agents and structured processing to extract information from research papers, then connects the paper-derived graph with product catalog data.

The aim is to make information that is scattered across prose, tables and product descriptions easier to explore. A user can ask what a device contains, which component was treated, what method was used, and what material result was reported. The supporting source and experimental context remain important parts of the answer.

Four entity types organize the graph:

| Entity type | Meaning | Examples in the demo |
|---|---|---|
| **Product** | A device or device model | A mobile phone; Nokia 5110 |
| **Component** | A part or assembly associated with a device | A battery, electrode, separator or printed circuit board |
| **Process** | A reported recycling or treatment route | Bioleaching, hydrochloric acid leaching or flotation |
| **Material** | A material or chemical constituent | Li, Co, Cu, graphite or LiCoO₂ |

A typical route through the graph is:

```text
Product --CONTAINS--> Component --PROCESSED_BY--> Process --HAS_OUTPUT--> Material
                         |
                         +---------------CONTAINS---------------------> Material
```

This is a useful reading pattern, not a claim that every paper supplies every link. Composition and treatment results are different kinds of evidence, and an extraction can be incomplete.

In the current published snapshot, the registered battery types are classified as Components, including batteries studied separately from the device they came from. Being the main subject of a paper does not by itself make a battery a Product.

## 2. What does the current demo contain?

The selected papers emphasize batteries, their constituent parts and material recovery. Two device-characterization studies also provide links between phone models, components and composition measurements. The catalog contributes **12 mobile phone records from GSMArena**; these are device specifications, not 12 battery recovery experiments. Only catalog records with existing direct connections to paper entities are included: nine model alignments and three weaker variant links.

| Item | Current snapshot |
|---|---:|
| Research papers | 20 |
| Product catalog records | 12 |
| Papers with archived extraction stages | 20 |
| Papers with authored walkthroughs | 6 |
| Walkthrough steps in total | 51 |
| Core Product, Component, Process and Material entities | 442 |
| Displayed relations at the individual-entity level | 1,564 |
| Quantitative RDF observations | 1,073 |

The graph export also contains family helper nodes: **469 exported graph nodes** in total. This is different from the 442 core entities. The four top-level entry groups and other browsing groups are generated by the interface and are not additional extracted entities. Scope and Observation records are represented through metadata and relation details rather than all being drawn as separate nodes.

These counts describe one frozen snapshot. They are not extraction accuracy scores, and the number of observations is not the number of independent studies.

The demo has three tabs:

| Tab | What it is for |
|---|---|
| **Knowledge graph** | Explore entities, relations, measurements and cross-source connections |
| **Extraction trace** | Inspect a paper's source text, tables and archived extraction outputs |
| **Paper** | Open the original publication pages and the GSMArena source |

The application reads saved files. Browsing does not call an extraction API, run the agents again, edit the research graph or calculate new measurements.

## 3. A quick first visit

For a short introduction, follow this route:

1. Open **Knowledge graph** and expand **Component**.
2. Open the **lithium-ion battery** group. Its members remain separate paper-specific samples.
3. Select a sample and inspect its source in the right-hand panel.
4. Open its neighborhood, then click a relation to inspect its evidence records.
5. On a record with a paper source, click **View evidence in replay**.
6. In **Extraction trace**, inspect the archived output and locate its source passage or table cell.
7. Use **← Back to graph relation** to return to that relation.

For a guided introduction, select the Aspergillus niger battery bioleaching paper in **Extraction trace** and click **Start walkthrough**. It shows why similar recovery values must retain their different treatment conditions.

## 4. Using Knowledge graph

### 4.1 Open groups and individual entities

The initial view has four entry points: **Product**, **Component**, **Process** and **Material**.

- Click a group to inspect its member list.
- Click **Expand group**, or double-click the group, to open it.
- Open a type or family group to reach individual source entities.
- Material expands directly into individual material nodes.
- Click an individual node to inspect its attributes, source and available Scope records.
- Use **Expand neighborhood**, double-click an entity, or select a neighboring entity to continue exploring its direct connections.

The node inspector also provides **Open paper replay** when the entity belongs to a bundled paper. Catalog nodes are not presented as paper extraction runs.

### 4.2 Understand the different kinds of groups

Not every group is an ontology class.

| Group label in the inspector | Interpretation |
|---|---|
| **TOP LEVEL** | One of the four main browsing entry points |
| **TYPE / FAMILY** | A grouping based on published types, family links, Scope metadata, categories or registered type aliases |
| **NAME GROUP** | A browsing group for otherwise unclassified Components with the same normalized full name |
| **Unclassified** | The interface has not established a grouping through the available rules |

For example, repeated `anode` entities can share a NAME GROUP while retaining distinct article identities. This does not assert that they have the same composition, chemistry or experimental history. Name grouping normalizes structural spelling differences such as case, whitespace and hyphens; it does not infer that two different terms are synonyms.

Published canonical types take precedence over older Scope spellings. Thus `lithium-ion battery` and `lithium ion battery` can belong to the same type group without merging their source samples. Conversely, unspecified batteries are not automatically assigned a specific battery chemistry.

Unclassified does not mean isolated or invalid. A uniquely named component may have useful relations while lacking a broader type declaration or another same-name sample. Conflicting registered aliases are not resolved by choosing an arbitrary candidate.

### 4.3 Search

Use **Find an entity** to search by entity name, type or source title. Useful starting points include:

- `lithium-ion battery`
- `Nokia 5110`
- `Co`
- `bioleaching`

The search results show source information because several entities can have the same name. Choose the result from the paper or catalog you intend to inspect.

Selecting a search result opens its direct neighborhood. Search is global: it clears the source, entity-type and relation filters to reveal the selected result. **Back** can restore the preceding view and its filters. This differs from the Top level and All entities buttons, which preserve those filters.

### 4.4 Filter the graph

The sidebar provides three selectors and one switch:

| Control | Effect |
|---|---|
| **Data source** | Restrict the view to one paper or catalog source and the connected endpoints included by that source's relations |
| **Entity type** | Show only the selected entity type |
| **Relation type** | Show only the selected predicate |
| **Show cross-source fusion links** | Include or hide the relations marked as fusion links |

Filters apply together. An Entity type filter can hide the other endpoint of a relation: for example, showing only Components hides their Material endpoints. To inspect a complete treatment route, leave Entity type at **All types** and narrow by paper or relation instead.

Filtered views can show nodes without visible edges because the relevant edges or endpoints have been hidden. This does not necessarily mean the published graph contains an isolated node.

### 4.5 Move around the graph

| Action | Operation |
|---|---|
| Inspect a node or edge | Click it |
| Expand a group or focus an entity | Double-click it |
| Reposition one node | Hold and drag the node; its attached edges follow |
| Pan the whole graph | Hold and drag empty canvas space |
| Zoom | Scroll, or use the **＋** and **−** buttons |
| Fit the visible graph | Click **Fit view** |
| Exit the current entity focus | Click **Clear focus** |
| Return to the grouped overview | Click **Top level** or the **Overview** breadcrumb |
| Show individual entities within the current filters | Click **All entities** |
| Return to the previous exploration view | Click **← Back** |

When the graph canvas has keyboard focus, `+` or `=` zooms in, `-` zooms out, and `Escape` performs Back navigation.

**Top level**, **Overview** and **All entities** preserve the current source, entity-type and relation selections, as well as the fusion-link switch. They clear the current drill-down route rather than clearing the filters.

After entity drill-down, Back restores the previous graph view, including its filters, layout, zoom and pan. Breadcrumbs instead navigate the group hierarchy. Explicit filter changes or group navigation start a new exploration route.

Dragging changes the display only. Layout changes are not saved to the KG and can be reset when the view is rebuilt.

### 4.6 Read arrows and group summary edges

Individual relation arrows run from subject to object. Dashed fusion links retain arrows so their direction remains visible.

At a collapsed level, an edge may summarize several underlying relations. Click it to see the direction breakdown and the original relations. A two-headed summary indicates that underlying relations exist in both directions; it does not make every predicate symmetric.

A group summary is not a new extracted triple or an average of the measurements underneath it.

## 5. Reading entities, relations and measurements

### 5.1 Source entities and shared materials

Product, Component and Process entities retain their source-specific identities. Two papers can therefore contain separate nodes called `lithium-ion battery` or use similar Process names.

Materials can be shared through canonical material identities. A shared Co node allows several studies to connect to cobalt without merging the studies' measurements.

Always inspect the entity's source and Scope before assuming that a repeated name describes the same object or population.

### 5.2 Common source relations

| Relation | Typical interpretation |
|---|---|
| **CONTAINS** | A product or component contains another part or material; its records may describe composition or component distribution |
| **PROCESSED_BY** | A reported input is associated with a treatment Process |
| **HAS_OUTPUT** | A Process has a reported material output or material-specific result |

These describe the intended reading of the relation types. The demo is an inspectable research snapshot, not a guarantee that every archived extraction has the correct endpoints or interpretation.

A qualitative HAS_OUTPUT relation can be present without a numeric recovery value. It is still an output statement, but it is not counted as a quantitative observation.

### 5.3 Inspect a relation record

Click an individual relation and examine the records in the right-hand inspector. Depending on the archive, a record can include:

- Value and unit.
- Measure or property, such as composition or recovery.
- Uncertainty and qualifier.
- Experimental conditions and Setting conditions.
- Source sample, sample state and measurement basis.
- Paper source and evidence quotation.
- Table identifier and cell-related metadata.

Use **View complete record JSON** for the full stored representation. Use **More records** when a relation has additional records beyond the first displayed set.

Several observations can appear on the same displayed relation. They remain separate records. Two recovery values of 100% may come from different treatment routes or conditions; their equal numbers do not make them duplicates.

Likewise, a composition percentage, recovery percentage and kinetic parameter describe different quantities. Read the measure, unit, sample state, method and conditions together. A raw stage may show a rejected or corrected interpretation that is not a valid final material output.

### 5.4 Process, Setting, condition and Scope

| Term | Role |
|---|---|
| **Process** | The treatment entity that connects a reported input with its outputs |
| **Setting** | A recorded experimental configuration associated with a Process |
| **Condition** | A particular circumstance or parameter, such as reagent concentration, temperature, duration or pulp density |
| **Scope** | Context describing the sampled population, model, batch or method family to which an entity or statement applies |
| **Observation** | A quantitative result with its own provenance and available measurement context |

Scope is not a replacement for the experimental conditions of a particular result. A paper-level battery population also does not establish that every named phone model in a catalog was experimentally measured.

## 6. Understanding cross-source fusion

Fusion connects information across sources while retaining source identities and evidence. It does not copy every observation onto one universal product node.

The current snapshot includes these cross-source link types:

| Stored predicate | Meaning and boundary |
|---|---|
| `observedForProductModel` | Aligns a paper-derived model designation with a catalog model. The nodes remain distinct; this is not proof of the same physical device. |
| `variantOf` | A weaker model-variant connection. Candidate scoring requires explicit matching brands, but a surviving link is not confirmed model identity. |
| `observedUnderScope` | Records a Scope-based applicability connection. Applicability alone is not evidence that a specific model was measured. |
| `comparableSamplePopulation` | Connects sample populations through recorded Scope evidence. The link alone does not establish that their measurements can be pooled. |

Family-membership links also support product and method grouping. They should not be read as experimental recovery results or entity identity assertions.

For example, a Nokia 5110 sample in a characterization paper can be linked to a Nokia 5110 catalog record. A battery fraction measured in that paper stays attached to the paper sample. It is not copied to the catalog record, averaged with other studies or made valid for every Nokia 5110 device.

The **Show cross-source fusion links** switch helps separate source-derived relations from the additional connections between sources. Inspect the link's basis and available Scope evidence when interpreting an alignment.

## 7. Using Extraction trace

### 7.1 Choose a paper

1. Open **Extraction trace**.
2. Use the single **Paper case study** selector. It lists all 20 papers alphabetically.
3. Click **Browse freely** to open that paper's archived stages.
4. If that paper has an authored guide, use **Start walkthrough** instead.

All 20 papers have bundled stage archives. Six additionally have guided walkthroughs; a disabled guide button for another paper does not mean its extraction trace is missing.

The workspace has two main panes:

- **Source text & tables** contains the archived paper text and parsed tables.
- The **output pane** contains records for the selected extraction stage.

Use the stage filter box to narrow the visible output records. This filter affects the current stage, not the fused graph or the original file.

### 7.2 Follow the stages

| Stage | What to inspect |
|---|---|
| **Table Gate** | Whether a table was accepted, skipped or treated as context, and the recorded reason |
| **IR / Execution** | Semantic interpretation, executable table instructions, verification or repair information, and emitted table facts |
| **Process** | Discovered treatment routes, descriptions and available Settings |
| **Entity** | Extracted entities, names, types, aliases and available evidence |
| **Relation** | Relation candidates, measurement fields, endpoints and unresolved binding requests |
| **Revision / Postprocessing** | Recorded reconciliation, corrections, removals, operations and execution status |
| **Scope** | Post-merge sample, model, population or method annotations |
| **Final relations** | The archived final relation set used for the paper's contribution to fusion |

The dependency map separates planning, grounded extraction and document completion. Table planning, Process and Entity work can occur in parallel. Document completion includes merge, optional revision, Scope and final serialization. **Scope follows merge/revision and precedes final export.**

This map explains stage roles. It does not prove that the displayed historical files were generated in one uninterrupted run. Archives have individual timestamps and may reflect different updates.

A stage can legitimately have empty or rejected outputs. A revision can be enabled but skipped, with no model calls or committed operations. Read the recorded status rather than assuming that a visible revision stage repaired a problem.

### 7.3 Locate text evidence

On a record, click **Locate text evidence** when a quotation is available. The source pane switches to Text and attempts to locate it.

| Location result | Interpretation |
|---|---|
| **Exact match** | The quotation was found directly |
| **Normalized match** | The quotation matched after permitted textual normalization |
| **Approximate match · navigation only** | A similar passage was found; this is a reading aid, not a new evidence assertion |
| **Choose a passage · navigation only** | Multiple candidates require a choice |
| **Summary search · navigation only** | A recorded Process summary is being used to find related text, not treated as a verbatim quotation |
| **No matching passage** | The current source text does not provide a usable match for the stored query |

Where a Process has only a summary, **Find related text (summary)** is available instead of a quotation-based action. Some records have no archived source quotation and therefore no direct text-location button. Missing evidence is not reconstructed from the entity name.

Candidate overlap percentages describe the navigation match, not the scientific correctness of a claim.

### 7.4 Locate a table cell

Click **Locate source table / cell** on a table-backed record. The source pane switches to Tables and highlights the stored table, row, column or cell when it can verify the reference.

The lookup uses table identity and archived coordinates, with raw cell text where available. Without usable coordinates, an unambiguous combination of row label, column header and cell text can support a match. A repeated value alone is insufficient.

The operation works in both directions:

1. Start from an extracted record and locate its source cell.
2. Or click a table body cell to inspect its archived extraction matches.
3. If several records match, choose a Table extraction or Final record version.

The two versions are not extra independent measurements. If no cell-level record is archived, the interface says so and can expose the relevant Gate decision. It does not invent an extraction for the cell.

Selecting Table Gate or IR / Execution initially selects the Tables source view. Selecting Process, Entity or Relation selects Text. A specific record with a table reference can subsequently switch back to Tables.

### 7.5 Move between the graph and a trace

From a graph relation, click **View evidence in replay** on the relevant evidence record. The trace panel can offer **Final record**, **Earlier output**, **Table Gate** or **Source scope**, depending on the available anchors.

The lookup uses source provenance, relation fields and evidence anchors. An earlier output is not selected merely because its numerical value resembles the final result. Ambiguous matches remain selectable rather than being silently replaced by the first candidate.

Use **← Back to graph relation** to return to the originating graph record. Use **Clear trace** to remove the trace-specific selection.

From a Final relations card, **View in graph** opens the corresponding graph context when it can be resolved. Intermediate Gate decisions, rejected candidates and IR instructions need not have a corresponding final edge, so this button is not offered on every record.

### 7.6 Download archived files

Each stage provides links to its bundled files where available. Common filenames include `llm_table1.txt`, `llm_table2.txt`, `llm_process1.txt`, `llm_process_settings.txt`, `llm_entity.txt`, `llm_relation.txt`, `llm_scope.txt` and `triples_final.txt`.

Use these downloads and complete record JSON to inspect details omitted from a card. The filename and stored file hash identify the artifact; a download is not a new extraction request.

## 8. Guided walkthroughs

Select the corresponding full paper title in Extraction trace to start one of these six guides:

| Paper / example | Steps | Main point |
|---|---:|---|
| Comprehensive mobile-phone characterization | 8 | Follow a phone model's battery fraction, then distinguish catalog alignment from measurement transfer |
| Smartphone Assessment | 8 | Keep battery composition, manufacturing cohorts, units and uncertainty distinct |
| Aspergillus niger battery bioleaching | 10 | Separate treatment routes, Settings and results with equal or similar values |
| Ultrasound-assisted Co and Li leaching | 8 | Distinguish treatment and control routes, and separate kinetic parameters from recovery outcomes |
| Anode hydrochloric acid leaching | 8 | Trace feed composition and treatment-specific lithium results with their conditions |
| Pyrolysis–ultrasonic flotation | 9 | Examine a failed table channel alongside surviving text results and incomplete coverage |

Each step provides a question, **What to inspect**, and a **Limitation**. The guide selects an existing archived record or graph target; it does not run an agent or generate a replacement result.

| Walkthrough control | Behavior |
|---|---|
| **Next →** | Advance to the next selected target |
| **← Previous** | Return to the preceding step |
| **Reopen step** | Restore the current step's intended record or graph context after free exploration |
| **← Return to step N** | Return from the graph to the active replay step |
| **Finish walkthrough** | Complete the last step |
| **Exit walkthrough** | End the guide and leave the current view available |

Changing the selected paper ends the previous guide. Guided graph stops can set their own focus, filters and fusion-link state so the intended example is visible; use Reopen step to return to that authored context. This is separate from ordinary Top level / All entities navigation, which preserves user filters.

If a recorded target is missing or ambiguous, the guide reports the problem instead of substituting another fact.

## 9. Suggested demonstration routes

### Route A: From a phone model to battery evidence

1. Search for Nokia 5110 and choose the paper-derived model entry.
2. Inspect a battery-fraction relation and its source.
3. Open its replay and locate the table cell.
4. Return to the graph and inspect the catalog alignment separately.

Explain that model alignment connects descriptions while measurements remain attached to their original study sample. The Comprehensive phones guide provides an eight-step version of this route, including the archived 45.4 battery-fraction cell.

### Route B: Compare battery treatment results carefully

1. Start the Aspergillus niger battery bioleaching guide.
2. Inspect the one-step, two-step and spent-medium route descriptions and Settings.
3. Follow the Li output records into their final graph context.
4. Read the conditions before comparing the values.

The guide separates the archived 100%, 100% and 95% Li results. Two equal 100% values remain different experimental observations.

### Route C: Show an extraction limitation

1. Start the pyrolysis–ultrasonic flotation guide.
2. Inspect the accepted table and its IR / Execution record.
3. Examine the rejected output direction and failed table repair.
4. Follow a surviving text result into the graph.

Explain that a text-derived result does not demonstrate successful extraction of the table or complete coverage of the paper. Table repair and document-level Process revision are separate mechanisms.

## 10. Interpreting the evidence

The demo is designed to make results inspectable, including limitations. In particular:

- A relation displayed in the graph is not automatically a manually verified fact.
- An archived LLM response can contain a mistake that was rejected or corrected later.
- An exact source-text match locates the quotation; it does not independently validate the interpretation of that quotation.
- Approximate highlighting and summary search help navigation and do not add evidence to the KG.
- A Process summary is not necessarily a verbatim passage from the paper.
- A Scope or model link does not establish measurement equivalence or justify averaging results across studies.
- The current graph includes reviewed offline corrections. Earlier stage files are preserved, so their labels, types or claims can differ from the final published graph.
- Empty or missing outputs are visible limitations, not facts that should be inferred from neighboring records.

For a quantitative comparison, check the source sample, material, measure, unit, method, experimental conditions and sample state. Distinguish initial composition, treated material and residual material before interpreting a percentage.

## 11. Troubleshooting

| Situation | What to do or check |
|---|---|
| The graph looks crowded | Select one paper or explore a group before using All entities |
| A relation is missing from the current view | Relax Entity type and Relation type filters; check whether the other endpoint has been hidden |
| The search opens a broader view than expected | Global entity search clears the three dropdown filters; use Back to restore the preceding context |
| Several nodes have the same name | Inspect their sources; they may be distinct study samples rather than duplicates |
| A Component remains Unclassified | It may lack a declared type, a unique registered match or a repeated full-name browsing group |
| No source sentence is highlighted | Check whether a quotation exists; inspect candidate passages, a summary-search result or the raw file |
| A cell has no extraction match | Inspect the table's Gate and execution record; the table may have been skipped, rejected or incompletely extracted |
| Start walkthrough is disabled | Browse freely; only six selected papers have authored guides |
| A graph record has no replay button | It may have no uniquely resolved bundled paper source or no appropriate archived record |
| Dragged nodes return to earlier positions | Layout changes are temporary and can be reset when the graph view is rebuilt |
| The page still shows old behavior | Reload it; if needed, perform a hard refresh to fetch current versioned scripts |
| Opening index.html directly shows no data | Serve the files over HTTP, or use the online demo; local file URLs restrict JSON loading |

## 12. Running locally and finding the files

The canonical project directory is `demo/ontoweee/`. From the repository root, run:

```sh
python3 -m http.server 8765 --bind 127.0.0.1 --directory demo/ontoweee
```

Open <http://127.0.0.1:8765/> and leave the server running. If that address already serves this demo, reuse it. No database, npm installation or model server is needed. Optional typography uses Google Fonts with local font fallbacks.

| File or directory | Purpose |
|---|---|
| `index.html` | Application entry point and active dataset paths |
| `app.js` | View controls, filtering, graph interaction and replay navigation |
| `hierarchy.js` | Display groups, canonical type grouping and same-name Component fallback |
| `replay.js` | Archived record rendering and source-location helpers |
| `trace.js` | Graph-to-archive matching |
| `walkthrough.js` | Guide navigation and target resolution |
| `style.css`, `redesign.css` | Page styling |
| `datasets/battery20/full-traces/data/graph.json` | Active graph projection |
| `datasets/battery20/full-traces/data/manifest.json` | Snapshot provenance and artifact fingerprints |
| `datasets/battery20/full-traces/data/cases/` | Paper sources and archived stage records |
| `datasets/battery20/full-traces/data/raw/` | Stage-file downloads |

The blog serves a self-contained copy from `MyBlog/source/demo/`, generated into `MyBlog/public/demo/`. The public entry is `/demo/`. Research inputs, build scripts and older experimental snapshots are not all required in that deployed copy.

Starting the demo does not require rebuilding extraction or fusion. Avoid running a data-export script merely to open the page: exporter defaults can refer to historical datasets. Use the active manifest and dataset-specific notes when deliberately updating the snapshot.
